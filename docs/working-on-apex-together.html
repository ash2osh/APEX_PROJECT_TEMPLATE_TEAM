Working on APEX Together

How several developers share one APEX application without quietly deleting each other's work — and the handful of things this deliberately does not try to solve.

The problem

One export can erase a colleague's day, and nothing warns you

Alice and Bob work on the same leave-request app. They share one APEX workspace and one application — they are both editing the same thing, live, the way most APEX teams work. They share the source through git.

The old single-developer tooling exported an app by replacing the whole folder: delete what's there, drop in what came out of the database. That's fine when the database is the only place work exists. It stops being fine the moment git holds something the application doesn't.

Alice
Fixes a broken condition on page 6 by editing the source file directly, and merges it. The fix is in git. Nobody has pushed it into the shared application yet.
Bob
Pulls. His folder now contains Alice's fix. The shared application — the database everyone actually edits — has never seen it.
Bob
Finishes his own work on page 7 and exports. The old guard checks "are there uncommitted changes?" There aren't — he committed. It lets the export through.
Result
The folder is replaced with the application's state, which has no fix. Alice's fix is deleted. Git records it as a deliberate deletion, so the merge raises no conflict. Nobody is told.
Why this one is nasty

Most mistakes announce themselves — a merge conflict, a failed build, a red test. This one looks exactly like Bob intending to delete page 6. Every tool downstream believes him.

The idea

Turn the arrow around

The old tooling treated the database as the truth and the files as a photograph of it. Every rule followed sensibly from that, including "replace the folder", because a photograph is always taken fresh.

Working as a team needs the opposite: git is the truth, and a database is somewhere you send it. That single flip is why this is a separate template rather than a setting — the two ideas produce contradictory rules and can't live in one repo. 

// before — the database decides, files follow
   database  ──export──▶  files            (replace everything)

// now — git decides, the database follows
   files  ◀──export──  the shared app      (merge, never replace)
   files  ──import──▶  the shared app      (rare, whole team pauses)

One supporting detail makes it work. The folder is named after the app's alias — employee-self-service — never its number. You all share one number in development, but test and production give the same application a different one, and the tracked source has to mean the same thing in all three. The number lives in a small local file that git ignores.

The daily loop

Three steps, and there's no "pull" in them

Because you all edit one shared application, your colleagues' work is already in front of you — it arrived the moment they saved it, not when you ran a command. There is nothing to catch up on, so the daily loop has no import step.

Build — normal APEX work

Open the App Builder and do whatever you were going to do. Nothing about this step changes.

Export — bring the app's changes back into git

Reads the shared application and merges it into the files. Because a clean export produces identical bytes every time, your diff shows real changes and nothing else.

team.py export-app employee-self-service

Commit — app and database changes together

If your change needed a database column too, its migration goes in the same commit. One reviewable unit: the page and the column it depends on.

Two things to know about sharing one app

Your export carries whatever the app currently holds — including a colleague's half-finished region, committed under your name. Export when the app is in a state you'd be happy to ship, and keep branches short.

Git branches don't isolate APEX work. The database has no idea what branch you're on, so whatever is in the app lands in whichever branch you export to. Migrations are hand-written files, so those do stay on their branch.

Import is not a daily command

import-app overwrites the application everyone is working in — including unexported work belonging to people who didn't run it. It's a coordinated reset, done with the team paused, not a way to refresh your copy. If anyone has unexported work in there, the tool refuses and tells you to export it first. That refusal is the most important one in the whole system.

The mechanism

How the export decides what to keep

Export compares three versions of every file and picks a winner. That's the entire trick, and it's worth understanding because it's what makes the opening disaster impossible.

  • Base — what the files looked like the last time they matched the application.
  • Theirs — what's committed in git right now, on your branch.
  • Mine — what just came out of the shared application.

If only one side changed, that side wins. If both changed the same file differently, nobody wins automatically and you're asked to look. Try the cases:

The important row

The first two are the opening disaster. Anything that reached git without passing through the shared application — a hotfix, a hand-edited file, a change merged from somewhere else — used to be deleted in silence by the next export. Here it simply survives: the application has no opinion about a file it never held, so there is nothing to refuse and nothing to lose.

Database changes

Write down the change, not the result

The old approach photographed the whole schema after every change. A photograph tells you what is, never what changed — and you can't hand someone a photo of a cake and ask them to bake it. It also can't separate Alice's change from Bob's, because one photo contains both.

So a database change is now a small file describing one step. Two files, actually: the change, and how to check it worked. 

-- migrations/20260906T143000__bob__delegation.sql

-- migration-version: 1
-- target: tables
-- depends-on: 20260906T101500__alice__leave-balance sha256:9f2c…
-- destructive: false

ALTER TABLE hr_leave_requests ADD (delegated_to VARCHAR2(100));

The header is checked strictly — an unknown line is refused, never ignored, so a typo can't quietly switch something off.

-- …delegation.verify.sql — proof it actually worked

SELECT 'delegated_to exists' AS assertion_name,
       CASE WHEN COUNT(*) = 1 THEN 'PASS' ELSE 'FAIL' END AS status
  FROM user_tab_columns
 WHERE table_name  = 'HR_LEAVE_REQUESTS'
   AND column_name = 'DELEGATED_TO';

Why the file name looks like that

20260906T143000__bob__delegation is a timestamp, an author and a description. The timestamp means two people on two branches never pick the same name or fight over the order. The author means you know who to ask.

Why depends-on matters

It's the one line doing real work. If your change only makes sense after someone else's, you say so — and you pin their exact file, so if they edit it afterwards, yours is flagged rather than silently running against something different.

Worth knowing

Nothing checks for a dependency you forgot to declare. Your verification will fail afterwards, but by then the SQL has run and Oracle has already committed it. Treat that line as real work, and look for it in review.

The shared database

When someone changes things by hand

You all share one development database, so somebody will eventually recompile a package in SQL Developer at 6pm without writing a migration. There's a command that notices: 

$ team.py check-drift

DRIFT  DEMO.PKG_LEAVE_RULES  (PACKAGE BODY)
       changed, but no migration accounts for it
       last modified 2026-09-06 15:22:41

Minutes, rather than discovering it months later when a release behaves differently in test. One subtlety it handles for you: changing a table automatically marks every package that uses it as invalid, even though nobody touched those packages. That's normal Oracle behaviour, so it's reported as information and never as drift.

All of it together

One ordinary Tuesday

Alice and Bob are both at their desks, both in application 100. Carol is on holiday — and she left three hours of unexported work on page 12 last Friday. She matters at half past four.

09:10Alice
Opens the App Builder. Bob's page 7 work from yesterday is already there — same application, so there's nothing to pull and nothing to import. She adds a Cancel button to page 6.
09:40Alice
The button needs a new column. She writes the migration without touching a database at all, then applies it. The column is now visible to Bob too — one schema. From this moment she owes the team a prompt merge of that file. 
team.py new-migration --author alice --slug cancel-reason --target tables
10:15Alice
Exports. Her diff contains her page 6 and Bob's page 7 in whatever state he left it twenty minutes ago — that's what a shared application means. She reads both, commits, and merges quickly, with her migration in the same commit.
11:00Both
Alice and Bob hit export within the same minute. Both succeed, neither waits. Nobody announced anything, because two reads into two separate folders cannot collide.
14:00Bob
Bob's export stops and writes nothing. A hotfix to page 6 was edited straight into the file last week and never pushed into the application, so git and the application now disagree about the same page.
14:05Bob
He's never resolved a git conflict in his life. He doesn't need to — he's asked one question in plain language: git has the hotfix version of this validation message, the application has the old one, which do you want? He picks, it's applied and verified, he commits.
16:30Team
The team needs to reset the application to a known commit. Whoever runs it announces it and everyone stops editing — this is the one operation that touches what everybody is inside of.
16:31Refused
The import takes a copy first, compares it, and stops: Carol's Friday work is still sitting in there, unexported. It names what would have been lost and the command that saves it. No flag overrides this — it's the most important refusal in the system, and it just rescued three hours of work from someone who isn't in the building.
What nobody did all day

Nobody ran an import to "catch up" — there was nothing to catch up on. Nobody announced an export. And nobody kept work private by leaving it on a branch, because a branch doesn't hold APEX work back: the application has no idea which branch you're on.

Honest limits

What this does not do

Every safety mechanism here has an edge. Knowing where it is beats being surprised by it.

Can't stop
Two people editing the same page at the same moment. You share one application, so this is settled inside the App Builder before any file exists: the later save wins and the earlier one is gone. Nothing here can recover it — APEX's own page locks are the only protection. This is the real price of sharing one app, and it's the same price you pay today.
Can't stop
Two people recompiling the same package at once. That happens inside the shared database, before any file exists. No tool can prevent it. Drift detection finds it quickly instead.
Can't stop
A half-finished migration. Oracle commits structural changes as it goes, so a migration that fails midway leaves real changes behind. It's recorded as unfinished and a human repairs it; there is no undo button.
Does do
Refuse rather than guess. Anything uncertain stops and says so, with the exact command to continue. A stop you can read beats a success you can't trust.
Does do
Keep a copy before it touches anything. Every risky step saves the current state first, so an interrupted operation is recoverable rather than a guessing game.
Getting it live

Test is automatic. Production is not.

Tagging a release builds one sealed package — the app source and every migration — and stamps it with a fingerprint. That exact package is applied to test automatically and checked.

Production receives the same bytes, verified against the same fingerprint, plus a written runbook. A person applies it. This repository has no production apply button and no credentials for one, which is a deliberate choice rather than an unfinished feature.

Where this stands

Design and implementation plans are written and reviewed; the tooling itself isn't built yet. The three plans build in order — the daily loop first, then migrations, then release and promotion — and the first one is useful on its own, because it's the one that ends the silent deletions.
