# APEX 26.2 template upgrade design

Date: 2026-10-08. Status: implemented and qualified inline; amended after Docker qualification and native skills-registry inspection. Git integration is authorized by the developer.

## Intent and authorized work

Preserve the existing template as a 26.1 maintenance line, then develop a
26.2 template that uses public Oracle APIs for team workflows. Retain separate
repositories per developer, shared DEV as runtime truth, numeric application
IDs, explicit environment mappings, and both Bash and PowerShell entry points.

The user authorized local branch creation, planning all five upgrade items,
and mandatory forced Oracle skills synchronization every week. The later real-test
request authorized disposable Docker application probes; the user separately
approved temporary developer creation/removal. Those probes are recorded in
[the live qualification report](../plans/2026-10-08-apex-26.2-live-results.md).
Implementation of the five features, schema migrations, commits and pushes
remain outside the work performed so far.

## Branch and release policy

1. Preserve `codex/apex-26.1` as the 26.1 maintenance line. A later, explicitly
   authorized maintenance commit labels that line and documents `--ref` pinning.
   Keep its existing tests and CI; do not apply downstream cleanup here.
2. Implement on `codex/apex-26.2-upgrade`; merge to `main` through a reviewed PR.
   Main becomes 26.2 only after the release gates below pass.
3. The initial 26.2 release supports the APEX 26.2 line and is qualified using
   SQLcl 26.3.0.0, the client used for full and existing-page partial imports
   in the Docker suite. Other builds require qualification; the partial wrapper
   remains gated on version/cutoff behavior as well as command availability.
4. Use manifest `schemaVersion: 2` with `apexRelease: "26.2"` and
   `minimumSqlclVersion: "26.3.0.0"`. Existing schema-1 upgraders reject the
   new manifest before installing files, preventing silent upgrades from main.
5. The new upgrader reads schema 1 and 2. It records an explicitly selected
   `templateRef` and `apexRelease` in the local template lock. Upgrades with no
   `--ref` reuse a recorded ref. Moving from an unknown/26.1 line to 26.2
   requires `--apex-release 26.2`; this is a compatibility choice, not a live
   database verification. Doctor and write preflight verify the actual release.
6. Instructions for existing 26.1 projects use the maintenance ref or the
   existing temporary-checkout bootstrap procedure for an explicit 26.2 move.
   Publishing the branches and creating a PR remain separate user operations.

## Global constraints

- APEX release line: 26.2; qualified APEX SQLcl floor: 26.3.0.0.
- Python 3.10+, standard library only; Bash 4.3+ and PowerShell 5.1+ parity.
- No custom database metadata tables, mutexes, checkout rosters, or ledgers.
- Credentials stay in saved SQLcl connections; no credentials in tracked files.
- All application commands use numeric IDs and explicit workspace/schema mappings.
- Shared DEV remains runtime truth; Git branches do not isolate database state.
- Full imports remain the only staging/production deployment route.
- Existing migration and ORDS export contracts remain unchanged.
- Keep drift checks, version stamps, exact source verification, and fail-closed
  baseline advancement. Full publish retains its whole-app guard; partial mode
  uses the reviewed selected-page guard and fresh whole-app verification snapshot.
- No automatic supporting-object installation, workflow-instance migration,
  theme upgrade, compatibility-mode change, or AI-provider conversion.
- Read `docs/known-limitations.md` before modifying accepted behavior.
- Commit and push only when explicitly requested.

## Mandatory weekly skills refresh

Proposed replacement for the previously added checkout-local success file,
following the user's 2026-10-08 decision. Implement the guidance changes after
final review; existing entry-point instructions still describe the old record.

At the start of every task, read SQLcl's own user-local registry:
`~/.dbtools/skills/skills.json` (under the current user's home on every platform).
Do not create or maintain `.sync-state/oracle-skills-sync.json`. The native
registry is shared by projects using the same user's installed skills; a fresh
installation need not be repeated just because another checkout starts a task.
Never copy this registry or its dates into the template or a downstream repo.

Use the Oracle repository's `repositories[].lastSync` for repository freshness
and its `commit`/`resolvedCommit` for reported version evidence. Also inspect
`installations[].installedAt` for every Oracle root in the agent's actual loaded
skill directories; `lastSync` alone does not prove those skills were installed.
The currently observed roots are `apex`, `db`, `fusion`, `graal` and `oci`;
discover the expected roots from the synced Oracle catalog so new roots are not
silently omitted. Expand `~` and match actual `targetPath` values, not only an
agent label: the common `.agents/skills` path can have multiple agent records.
Deduplicate identical target paths; conflicting duplicate records are invalid.
Require an installation record and an existing `SKILL.md` for each expected
root in each loaded Oracle skill directory. Do not use file modification dates.

A missing/unreadable/malformed registry, missing repository or required
installation, missing installed skill, invalid/future timestamp, unknown catalog
or conflicting evidence makes freshness unknown and triggers a forced refresh.
If any required repository or installation timestamp is seven days old or older,
refresh automatically. Report the oldest relevant installation timestamp as
the installed-skills freshness date rather than the newest record anywhere on
the machine. Require explicit UTC timestamps and compare against current UTC.

When due, start SQLcl without a database connection (`sql /nolog`) and run
`skills sync -force` for all Oracle roots, or use MCP
`skills_sync(force=true)` with all roots selected. Check live completion and
conflicts, then reread the native registry and confirm the relevant installed
paths and timestamps are current. Never manually write, repair or advance its
records. Notify the developer in the current chat that the automatic forced
sync completed, with its verified date and available installation count. When
already current, report the recorded installation date without claiming a new
sync or claiming that an earlier run used `-force`.

SQLcl 26.3's registry stores repository and per-installation timestamps, but no
persisted force flag or whole-run conflict/success verdict. The user chose native
freshness evidence instead of the stricter custom completion receipt. A later
task cannot infer a previous run's `-force` option or complete success from this
registry. Verify those facts from the current run when a refresh is performed;
do not describe this design as preserving the old receipt's audit guarantee.

If refresh fails, conflicts, or the registry remains unverified, report that
outcome and block Oracle/APEX implementation or live operations for the task.
Read-only investigation/planning can continue. SQLcl may update repository or
some installation timestamps during an unsuccessful overall run; fresh dates
must not override a failure observed in the current task. Do not edit the native
registry or synthesize a success record to conceal the failure.

Preserve project-authored `.agents/skills/` and `.claude/skills/`, inspect Git
status before/after refresh, and use APEXlang skills matching the target release.
No standalone automation is required: inactive checkouts check freshness at
their next task startup. The initial forced sync installed 40 skills without
conflicts. Native metadata inspection found repository `lastSync` at
`2026-10-08T05:13:11.520090041Z` and installation dates at
`2026-10-08T05:13:11.538803622Z`, commit
`6c57a52588c2a68e261ff0542b8fde80fd2b9c42`. These are SQLcl-owned timestamps,
not the later timestamp previously written into the custom receipt.

## Item 1: Native application locking

Add `APEX_WORKSPACE_USERNAME`, a single existing workspace developer or
administrator username for the selected workspace. It is independent of the
database session user and of `DEVELOPER_NAME`, which remains the version label.
Expose this requirement in `.env.example`, the initialization questions, doctor,
and the final review summary. Do not infer it from `DEVELOPER_NAME`, schema or
saved-connection name. Resolve it against the selected workspace's public user
metadata and require an existing developer/admin before locking; preserve the
server's canonical username. Workspace login names can be email-style strings,
so do not apply the Oracle schema-identifier or version-label regex. Parse the
value literally, reject control characters, and bind/escape it as a SQL value.
Require it only for APEX locking/publishing checks, not unrelated schema/ORDS
commands or offline template upgrades. One configured username must be valid
in every workspace targeted by that checkout's DEV locking operations.

Public API signatures verified from the installed package and Oracle docs:

```text
LOCK_APPLICATION(p_application_id NUMBER, p_lock_as_user VARCHAR2,
                 p_lock_comment VARCHAR2)
UNLOCK_APPLICATION(p_application_id NUMBER, p_unlock_as_user VARCHAR2 DEFAULT NULL)
```

Expose `team.sh app-lock <id> --env dev [--comment <text>]` and
`team.sh app-unlock <id> --env dev`, with equivalent PowerShell commands.
Reject absent applications, working copies where the public API is inapplicable,
invalid workspace users, mismatched targets, and locks belonging to others.
Manual unlock always supplies the expected developer; never use the unfiltered
null-owner form. `--force` for publishing does not authorize breaking a lock.

For publish, acquire a native lock before the final live-state comparison and
retain protection through import and verification. Use an opaque run ID in the
comment and verify owner/comment before releasing. Refuse to adopt a preexisting
lock, including one held by the same owner. Store a machine-local recovery note
under `.sync-state/` after acquisition, containing IDs and public lock evidence.
An ambiguous import/ownership check retains recovery evidence and the previous
baseline. Release only a demonstrably owned lock; never erase another lock.

Oracle makes repeated same-owner requests succeed. Consequently, this API
cannot promise exclusive ownership per process. Document the residual race for
simultaneous requests using one workspace developer, keep existing detection,
and require developers to avoid overlapping operations with the same account.
Do not describe native locks as a replacement for human coordination or as a
way to recover unsaved Builder edits.

Docker qualification found that full and page-only imports preserve the native
lock but do not enforce it: both imported despite another owner. Successful
lock acquisition in the wrapper is therefore mandatory before any import.
Commit acquisition explicitly. Only cooperating callers using different developer
accounts are excluded by this mechanism; it is not protection against direct
SQLcl imports or same-account concurrency. Repeat preservation checks through
the implemented wrappers. If import drops the lock, the automatic flow fails its
release gate; do not substitute check/relock and claim continuous protection.

## Item 2: Deployment-file handling and verification

Replace duplicated Bash/PowerShell descriptor parsing with
`scripts/deployment_descriptor.py`. Required values remain `workspace.name`,
numeric `app.id`, and `app.databaseSession.parsingSchema`. Preserve the existing
same-schema and mapped target-schema checks. Validate supported 26.2 optional
properties, JSON types, subscription app-ID mappings, and checksum-salt format.
Unknown properties are refused with a precise key path, not silently dropped.

Honor the explicitly selected `deployments/<env>.json`. Do not silently merge
`default.json` into it: Oracle selects a deployment file rather than overlaying
every file. Resolve absent properties from the source/target defaults using
the compiler and observed export. Do not set competing installation API or CLI
overrides outside the validated descriptor.

Separate exact source verification from effective deployment verification.
Generated `default.json` remains local/ignored. Include its effective values
in verification and export evidence; compare checksum salts without printing
their values. An identity-only selected descriptor did not retain the preceding
salt in its export during qualification; salt preservation requires an explicit
selected value and a matching exported value. Detect wrong workspace/schema/ID, runtime flag or subscription
mapping mismatches, and unchanged/replaced salts where preservation was chosen.
Do not add deployment files to the Graphify corpus.

Preserve exact bytes for source including binary static files and 26.2
`generated-artifacts/translations.sql`. If a supported deployment override is
materialized back into `.apx` on export, compare the precise documented
property against the descriptor instead of weakening general byte checks.
Unrelated byte differences still fail. Qualification must pin which override
properties materialize and how they are represented.

Supporting objects can be exported but are never installed/deinstalled as an
implicit extra action. Detect source that requests automatic installation and
refuse unless that database effect was explicitly authorized. Keep schema
migrations in the existing migration workflow.

## Item 3: Explicit source upgrade

Add `team.sh upgrade-apexlang <id> --env dev --mode builder|files` and its
PowerShell equivalent. The command is a separately requested operation.

- `builder`: export the current live application to fresh scratch space without
  importing. This is the appropriate path when shared Builder is authoritative.
- `files`: first back up/observe the live application and refuse unreviewed
  drift; then import the reviewed local files and export the result to fresh
  scratch space. Preserve target identity and all item-1 protection.

Require a clean source tree and verified 26.2 target. Preserve authored
`dev.json`, `staging.json`, and `prod.json`. Install the canonical new export
atomically, removing obsolete files through the existing staged replacement
pattern. Do not use Oracle's destructive in-place `-force` example on authored
source. Keep previous source/recovery evidence on partial failure.

Record old/new format metadata and exact file changes in a local upgrade report.
Do not invent the `.apex/apexlang.json` version structure; use qualified real
fixtures. Verify the new canonical export is stable on a second export before
advancing a baseline. Structural changes are reviewed in a dedicated commit
when authorized, separate from feature edits. Do not import old 26.1 baseline
markers into normal 26.2 publish as if they were newly verified.

Use `CREATE_WORKING_COPY(p_application_id, p_working_copy_name,
p_working_copy_description DEFAULT NULL) RETURN NUMBER` and print the returned

Inspect is read-only. Creation does not silently export or publish either app.

do not isolate database migrations. Integration into the main application is a
separate, coordinated Builder comparison/merge or reviewed source reconciliation
and publish operation. Any future implementation must avoid invented merge APIs
and automatic promotion/deletion of copies.

## Item 5: Optional DEV partial publishing

Add repeatable `--file <app-relative-path>` to `publish <id> --env dev` only
after a documented real SQLcl file-import command has passed local qualification.
If the installed client does not support the required command, refuse before
any database write and report the qualified client requirement. Keep full
publish as the default; staging/production reject `--file` before connecting.

The first version accepts existing `pages/*.apx` files only. Reject new/deleted
pages, page 0, shared components, deployment files, generated artifacts, static payloads,
links, absolute paths, traversal, duplicates, and files outside the app root.
Broader file types require a later design because dependency and deletion
semantics differ. Validate the full source with the correct compiler first.

Extend export-baseline evidence to schema 2 with per-source-file SHA-256 hashes.
Missing/old content evidence requires a full export. Refuse a partial publish
when any unselected source changed locally, was added, or was deleted; never
mark those files as published. Keep native application-lock acquisition, but
use a selected-page content guard for partial mode rather than treating every
app timestamp/version change as selected-page drift. Full publish retains its
existing whole-app guard. Under the application lock, take a fresh stable
whole-app export and require each selected page's bytes to equal its baseline.
Unrelated live page/shared-component changes can be incorporated in the fresh
snapshot; a changed selected page requires reconciliation before import.

Build a private staging tree from that fresh live export and replace only the
selected pages with the reviewed local edits. Preserve the explicitly selected
authored descriptor and verify its effective values before any write. Validate
this whole merged tree, so references are checked against current shared
components rather than a stale checkout. Generate the version tag from the
fresh live manifest's version base using the existing developer-tag convention;
never overwrite a newer base/version with a stale local manifest. Stamp the
expected version in the staging tree only using the existing helper,
then update the live version with public `SET_APPLICATION_VERSION` after the
selected import, rather than importing the whole manifest as a hidden selection.
SQLcl 26.3.0.0 successfully imported one existing page with `apex import
-input <app-dir> -deployment <descriptor> -files <absolute-page-path>`.
The version API added/advanced generated deployment
`app.sessionStateProtection.allowUrlsCreatedAfter`, matching the live
`last_updated_on` in the generated-26.2 starter probes. The authentic-26.1
conversion fixture omitted that property and changed only `application.apx`.
Verification must permit those two measured file sets, with byte equality of
all other source and exact deployment equality after removing only the cutoff
field. Do not assume the cutoff is always exported or infer why it is omitted.
Bookmark behavior and explicit cutoff preservation remain release gates.
Do not enable partial publishing until those effects have been qualified and
accepted; keep all unrelated deployment differences as failures.

Re-export and verify the whole app plus deployment effects. Advance the baseline
only when selected changes and the version stamp are present and all other
source matches the fresh pre-import live snapshot exactly. Compare against that
snapshot, not the old local checkout. On success, atomically install the verified
canonical export locally, preserve authored descriptors and unrelated protected
files, and record the new whole-app baseline with all observed source hashes.
Require all unselected local files clean before this replacement; do not erase
unpublished work. Report that unrelated live updates were synchronized and
require normal generated-diff review. On failure, retain the old baseline and
original local source plus scratch recovery evidence. An import followed by
failed stamping/verification is an unverified write, not a clean rollback; retain recovery evidence and old baseline.

### Page ownership and the qualified team-notice exception

The user wants routine partial publishing of exclusively owned pages to avoid
an extra team notice. Treat this as a conditional workflow improvement to
qualify, not as proof supplied by local Git history or a developer's version tag.

Read-only inspection of the Docker APEX 26.2 installation on 2026-10-08 found
`LOCK_APPLICATION` and `UNLOCK_APPLICATION` on public APEX APIs, but no exposed
public page-lock routine. Oracle documents page locks through Builder's Page
Designer, application home page and Page Locks utilities. SQLcl can inspect the
public `APEX_APPLICATION_LOCKED_PAGES` view, whose installed columns include
workspace, application ID, page ID, lock ID, owner, comment and lock timestamp.
No current locked pages were visible in the verified DEMO workspace. That empty
result does not qualify lock preservation or enforcement during a page import.
Do not invent `APEX_PAGE.LOCK_PAGE`, invoke private `WWV_*` routines or update
APEX internal tables to automate page locking.

For now, page locks must be acquired in Builder. Add read-only SQLcl ownership
checks using the public view; acquire no page lock as an incidental preflight.
The configured `APEX_WORKSPACE_USERNAME` must own every selected page's lock.
Qualify what happens to those locks during partial import and whether Builder
blocks another developer's edits, including an already-open page editor. Capture
lock evidence before editing/export baseline creation and recheck the same lock
IDs/owners immediately before import and after export verification.

Keep the existing pre-publish coordination rule until a separate release gate
allows a routine page-only exception. Eligibility requires all of the following:

- Existing DEV pages other than page 0; every local source change is selected.
  No shared-component, descriptor, schema, supporting-object or global-page edit.
- Verified Builder page locks owned by the configured workspace username before
  baseline capture and still matching at publish/verification; a missing,
  replaced or differently owned lock refuses the exception.
- Normal application lock acquisition, full compiler validation, whole-app
  selected-page byte/lock drift checks and whole-app byte/deployment verification
  still pass. Unrelated live changes are incorporated only through the explicit
  fresh-snapshot staging/verification flow above. A changed selected page refuses;
  full publish keeps its existing whole-app drift/version checks.
- Real qualification establishes the version/cutoff and application-lock effects
  on other pages and sessions. The observed `allowUrlsCreatedAfter` change is
  app-wide; page ownership alone does not make the publish page-scoped.
- The selected authored DEV descriptor explicitly supplies a checksum salt and
  ISO-second URL cutoff, both matching live generated deployment evidence before
  and after importing. An implicit salt or cutoff refuses this exception. Native
  testing showed that a cutoff-only descriptor could advance protection metadata.
- Page IDs and aliases remain unchanged; an alias change requires coordinated
  full publishing.
- Teammates use separate workspace usernames and the agreed guarded workflow;
  raw SQLcl writers and administrators overriding locks are not excluded by it.

If these gates pass and the reviewed policy accepts the measured app-wide
metadata effects, routine eligible page-only publishes may omit a new team
notice. Failed eligibility cannot silently downgrade to an uncoordinated import.
Full publishes, page 0/shared edits, and uncertain ownership retain coordination;
ambiguous writes or a retained application lock require recovery communication.
This describes human workflow requirements, not authorization for an agent to
send Slack/email messages. Current-chat status and error reporting remain.

## Final qualification amendment (2026-10-08)

The guarded page-only route is implemented. Native Builder tests refused another
owner's already-open editor save and preserved exact page locks during selected
imports; full imports removed those page locks. Runtime bookmarks passed valid
and tampered controls before/after selected imports and public version stamping.
Both wrappers passed the explicit-salt-and-cutoff no-notice route, unrelated live
page synchronization, subscription remapping and translated-artifact round trips.
Exports include `-exptranslations`. Canonical 26.2 files conversion verifies exact
source bytes; genuine 26.1 format conversion still requires human structural-diff
review. Unknown deployment properties and supporting-object execution remain
refused. See [the qualification guide](../../apex-26.2-qualification.md) for evidence
and limits. Windows-native live coverage and an independent reviewer were not
available; the human requested inline implementation without subagents.
