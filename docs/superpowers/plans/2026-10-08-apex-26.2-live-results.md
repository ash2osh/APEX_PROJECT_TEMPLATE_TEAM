### Lock behavior

All operations used `APEX_APPLICATION_ADMIN` in explicit workspace context.

- A lock rolled back from a clean state was absent in a separate SQLcl session;
  explicit commit persisted acquisition. Commit is also needed for release.
- A repeat request by `DEMO` succeeded and replaced its comment. Consequently,
  the native API does not serialize processes using one workspace account.
- `APEX262_PROBE` could not acquire a lock held by `DEMO`: `ORA-20001`.
- Wrong-owner release was refused with `ORA-20001`; case-insensitive release
  using `demo` succeeded for `DEMO`'s lock.
- An unknown workspace developer was refused with `ORA-20003`.
- Full import changed the selected page while preserving the other developer's
  lock owner, comment and timestamp. Page-only import likewise preserved owner
  and comment while applying the edit. **A native lock does not make raw SQLcl
  imports refuse another owner's application.**
- Comparing the whole export after the full locked import with its canonical
  baseline found only the intended page change; lock metadata did not change
  exported source bytes.

Wrapper cooperation remains essential. Refuse a preexisting lock, including
one belonging to the same account; acquire before the final drift check; verify
owner/run comment through import and export; release only the lock that this
operation demonstrably owns. Keep human coordination and recovery evidence.
Same-account concurrent acquisition and writers bypassing the wrapper remain
limits, even though imports preserve the native lock.

### Deployment materialization

The selected `dev.json` contained explicit workspace, numeric ID and parsing
schema, plus a distinct application name, `debugging: true`, `logging: false`,
and a generated checksum salt. A conflicting `default.json` contained another
name, opposite flags and a different salt.

Native import applied only the selected overrides. Public live reads confirmed
the name and runtime flags. The following export returned the selected salt
exactly; salt comparisons were performed without printing its value. Compared
with the baseline, only `application.apx` and `deployments/default.json` changed.

A second import selected an identity-only descriptor while keeping the
conflicting default in the input folder. The default's overrides were not used;
the original source name and flags returned. The generated deployment export
also no longer contained the preceding selected salt. An identity-only file is
therefore insufficient evidence that a previously deployed salt was preserved.
This observation concerns the exported deployment representation; no private
APEX table was queried to infer an undocumented salt value.

### Authentic release conversion

Input came from Oracle's synced 26.1 `example-0`, retaining its original
`.apex/apexlang.json` value `26.1.0+3102`. Only fixture identification, a generated
salt and the explicit Docker deployment descriptor were substituted. Its empty
deinstall script was inspected; no supporting installation was requested.
The source format marker was never rewritten to simulate an upgrade.

The 26.2 server accepted the 26.1 import. Two fresh exports produced the same
23-file tree, with metadata `26.2.0+3479`. All five PNG assets matched their input
SHA-256 hashes. The original scratch source retained its 26.1 format marker.

Observed layout changes:

- `breadcrumbs.apx` became `breadcrumbs/breadcrumb.apx`.
- `lists.apx` became `lists/navigation-bar.apx` and `lists/navigation-menu.apx`.
- `lovs.apx` became `lovs/boolean.apx`.
- The empty `supporting-objects/deinstall-script.sql` was absent from the export.
- The authored `deployments/dev.json` was not emitted by export; export generated
  `deployments/default.json`. Source replacement must preserve authored files.

These results qualify this minimal example. They do not prove that arbitrary
supporting-object scripts or translated application artifacts survive conversion.

### Page import and version stamping

The entire staged app first passed disconnected compiler validation. The source
contained one selected page edit and a different edit to an unselected page.
The actual SQLcl 26.3 command was:

```text
apex import -input "<app-dir>" -deployment "<app-dir>/deployments/dev.json" -files "<app-dir>/pages/p00001-home.apx"
```

It reported `Import successful.`. The subsequent whole-app export differed
from the canonical baseline only at `pages/p00001-home.apx`. The unselected
login page and all other files remained byte-identical. Raw SQLcl ignores the
unselected local edit; the proposed wrapper must detect and refuse that state
before writing so that it cannot advance the baseline over unpublished edits.

Next, `SET_APPLICATION_VERSION` followed by commit applied the normal version
tag, verified with `GET_APPLICATION_VERSION` and the exported manifest. Its
export differed at `application.apx` **and** `deployments/default.json`.
The only deployment difference was addition of
`app.sessionStateProtection.allowUrlsCreatedAfter`. A second version update
advanced that value. In both cases it exactly matched the live application's
`last_updated_on` timestamp. Repeating the export without another write was
byte-identical.

The verifier must account for this exact measured key and server timestamp;
it must not discard the generated deployment file or ignore arbitrary changes.
The API documentation's basic version setter description does not establish
the runtime consequences of that cutoff. Bookmark behavior and explicitly
configured cutoff preservation still require qualification before enabling the
page-only wrapper in a release.

## Release gates recorded before implementation

- Implement the production modules, safety checks and CLI parity; run these
  scenarios again through the supported wrappers.
- Qualify interruption, timeout, ambiguous writes, lock loss/recovery and
  concurrent processes. Sequential owner tests are not a concurrency proof.
- Qualify version/cutoff behavior with real bookmark URLs and explicit cutoff
  settings; decide whether the measured stamp side effect is acceptable.
- Qualify translated apps, subscriptions, nonempty supporting objects and
  broader descriptor shapes as required by the active design. Working-copy
  synchronization is deferred with the feature.
- Qualify PowerShell/Windows behavior. Current live tests used Linux SQLcl.
- Use 26.3.0.0 as the qualified APEX client floor for the active four-item
  release. Older clients and other 26.3 builds were not qualified for this suite.
  A newly started MCP session must report the intended version before it is used.

Recommended implementation order remains compatibility and locks, deployment
verification, canonical source conversion, then optional partial publishing after its additional version/cutoff gate passes.

## Follow-up: public page-lock interfaces

Read-only Docker inspection on 2026-10-08 found only application-lock setters
among the installed public APEX lock routines; no public page-lock API was
exposed. The public `APEX_APPLICATION_LOCKED_PAGES` view is available, with
`WORKSPACE`, `APPLICATION_ID`, `PAGE_ID`, `LOCK_ID`, `LOCKED_BY`, `LOCK_COMMENT`
and `LOCKED_ON` columns. In verified DEMO workspace context it returned zero
current locks. No APEX state was changed by this follow-up.

Oracle's [page-lock documentation](https://docs.oracle.com/en/database/oracle/apex/26.2/htmdb/locking-and-unlocking-a-page.html)
describes Builder operations. A no-team-notice page-only route therefore requires
Builder-acquired locks and new live tests of page-lock enforcement/preservation,
plus the already pending app-wide version/cutoff qualification. Existing SQLcl
application-lock tests do not prove page-lock behavior. The proposed owner setting
is `APEX_WORKSPACE_USERNAME`, independent of the database username and version
author tag. This follows the public-API-only policy; no private page-lock calls
are proposed.

The later proposed partial-mode page-specific drift guard, fresh-live merged
staging tree and atomic local synchronization have not been implemented or
qualified by the earlier primitive import tests. Test unrelated live page edits,
selected-page conflicts and current shared-component references through those
wrappers before enabling the revised workflow. Full publish retains the current
whole-app drift guard.

## Implementation probe follow-up

The reusable harness reconfirmed native owner conflict/reentry, raw full/page
imports preserving another owner's lock, canonical 23-file conversion and binary
preservation, and an unchanged unselected dirty login page. The authentic 26.1
fixture's first version stamp changed only `application.apx`; its generated
deployment export omitted `allowUrlsCreatedAfter`. Earlier generated-26.2 starter
probes changed both application source and cutoff metadata. These observations
do not establish the cause of omission or qualify runtime bookmark behavior.
Verify only the two measured file sets and reject unrelated source/deployment
changes. Public metadata represents debugging enabled as `Allowed`, and logging
disabled as `No`; boolean descriptor verification must use those observed values.
All retry cleanups used the exact fixture alias and owner/run-comment guard.


## Completed implementation qualification (2026-10-08)

The earlier primitive probe gates were subsequently exercised through the
supported Bash and PowerShell-on-Linux wrappers. Native full publication,
owner-filtered locks/recovery, selected-page publication with unrelated live
work, subscription master remapping, and canonical Builder/files conversion
passed. A seeded/published French-language fixture retained native generated
translation SQL and binary assets through full/partial imports and conversion.
Exports now include `-exptranslations`.

Actual Builder enforcement refused another developer's already-open editor
save; selected imports retained exact page locks while full imports removed them.
Actual runtime bookmarks passed valid and tampered controls before/after selected
imports and public version updates. The optional no-notice route passed both
wrappers with explicit live-matching salt and cutoff plus pre-edit page locks.
Cutoff-only/implicit-salt protection refused after its native side effect was
measured; the production preflight now requires both values. These tests do not
prove human account exclusivity or serialize raw SQLcl writers.

The final offline run passed 1,059 tests with 21 platform-specific skips.
Windows-native live signal behavior remains unavailable. Working copies remain
deferred, and executable supporting-object installation remains refused rather
than implicitly tested as an authorized migration. No custom database team
objects were created. Original application bytes were not compared.
